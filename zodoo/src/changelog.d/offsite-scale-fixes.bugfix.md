Three scaling defects, found by measuring the real backup server rather than guessing: it writes 410 MB/s to local disk but only **8.5 MB/s** to the NFS store, which is the ceiling for all customers together (184 GB in a six-hour night). WAL is irrelevant at that scale; base backups are the whole problem, which makes incremental base backups the condition for running a hundred instances rather than an optimisation.

The minutely WAL job ran at the same second on every instance, because they all use `* * * * *` — a hundred machines uploading simultaneously. Each now waits a *stable* offset derived from its project name, so a machine keeps its own second and consecutive runs cannot overtake each other.

And one manifest per run meant hundreds of files per day per area on a busy database, while the completeness check reads the manifests of *all* areas — millions of small files a year at a hundred instances. Manifests are now one file per day with one JSON line per run, appended rather than replaced, which fits the write-only model exactly: adding yes, changing and deleting no. Earlier lines stay untouchable, so "a source may never declare less than it did before" still holds.
