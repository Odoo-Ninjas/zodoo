Rewriting `docker-compose.yml` from inside a container whose home differs from the host's silently produced a broken instance. Bind mount sources are resolved by the docker daemon on the *host*, but zodoo wrote the paths it saw *in* the container - running `odoo reload` from the robot image (whose user has `/opt/robot` as home, see `useradd -d`) turned every source into `/opt/robot/.odoo/...`, which does not exist on the host. The containers then came up with empty mounts, i.e. without their code, and died with `ModuleNotFoundError: No module named 'zodoo'`; the only visible symptom was that the instance never answered again, so anything waiting on it hung until it was killed. This bit zebroo-sync's `test_millions` suite, which reconfigures its own instance from the test: green until 2026-08-08, then failing, then running into the CI job limit for weeks - the trigger was the (correct) fix that finally let the robot user write into its real home, which made the previously ineffective rewrite actually happen. Writing the compose file now aborts with an explanation when the paths in the existing file belong to a different home than the current process, naming both paths. Commands that only talk to a running instance (`odoo shell`, `psql`, `robot run`, ORM access) are unaffected, and `ZODOO_ALLOW_CONTAINER_RECONFIG=1` overrides the check.
